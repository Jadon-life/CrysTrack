## Decision: scoped account information, not a restorable backup

Existing multi-request REST reads cannot establish a consistent snapshot across legacy tables without revision fences. A new additive **0024 local-only read RPC** is needed: one STABLE PostgreSQL statement snapshot, explicit authenticated-owner checks plus existing RLS; bounded 250-row internal pages. No source-table writes, task recovery, closures, financial calculations, reward claims, new persistent tables or service key. A small separately audited owner-only AI reader requires SECURITY DEFINER solely to apply the existing private consent-revision provenance filter; it never returns leases or request payloads.

Format: versioned UTF-8 JSON. Completeness means all rows of the selected, explicitly projected datasets at one DB snapshot, within documented limits; never all account bytes. Oversize, malformed ownership, unavailable source, auth loss or AI revision drift fails the entire download. No recent-only fallback. Original DB timestamps and timezone strings retained; numeric money/progress and bigint fields become exact decimal strings. Only closed verified daily records are verified historical evidence; open/incomplete headers remain labeled unchanged.

All categories are explicit choices. User-entered notes/chat may contain sensitive text and are included only after a clear archive warning and confirmation. User content is not scanned, summarized, logged or sent to an AI provider. Technical secret-bearing columns and opaque transport metadata are not selected. Cross-owner direct links fail closed rather than leaking a foreign ID or silently dropping an owned row. Historical frozen routine keys deliberately need not reference a still-live routine.

## Consistency and bounds

One read-only STABLE RPC under authenticated RLS projects an explicit schema allowlist, not `SELECT *`. Dataset scans count a maximum 10,001 rows first and measure projected bytes before collecting pages. Maximum 10,000 rows per dataset, 25,000 total and 8 MiB projected data; larger scopes fail explicitly with advice to select fewer categories (no successful truncated export). Network read cancellation/deadline and bounded browser download accumulation are enforced. No file is offered until the complete document, declared byte lengths/counts and SHA-256 digests have been verified. Approximate preflight counts are informational; final manifest uses snapshot counts. AI revision and authenticated owner are checked again before response delivery and client save. A download cannot retract bytes already deliberately saved; consent is assessed for the snapshot and rechecked before release.

No account restore, deletion, bank integration, finance behavior change or hosted rollout. Issue #18 remains a hard release blocker.

The new POST `/api/account/export` is a read-only operation, but remains in the conservative Preview writer inventory: every POST is denied in Preview before any real client is created. This does not enable a new Preview read allowlist. The manifest also provides per-category totals and a SHA-256 hash of the exact field projection registry. Checksums detect corruption; they are not a signature certifying an edited file's authenticity. PostgreSQL timestamptz retains exact instants/microseconds, not the user's original textual UTC-offset spelling. Archives preserve those instants and all stored scheduling timezone identifiers.

Export UI uses fresh direct Auth reads without calling the context's state-updating refresh helper: exporting should not retrigger unrelated profile-update effects. The client retains no archive in React state/storage and releases it after a verified download; cancellation/account changes fence late results. The bounded receiver uses a fixed 12 MiB byte buffer rather than an array growing with network chunk count.

Frozen schedule JSON is the one structured JSON column included: it is generated by the existing immutable schedule-capture engine, and the HTTP archive validator enforces only weekday/start/end date fields before release. Arbitrary opaque JSON objects are not exported. Invalid projected IDs, timestamps, decimals, schedule structure, duplicate identities or count/key mismatches fail the file rather than inventing a fallback.
